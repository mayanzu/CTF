## 解题过程

### 1. 先核对附件与文件类型

用 PowerShell 列出下载目录最近文件，确认目标 ZIP 文件名、大小和时间；复制原 ZIP 到本题目录并计算 SHA-256。检查 ZIP 目录后，发现其中只有一个 EXE；解压后再计算 EXE 的 SHA-256。

PE 头检查结果：`pei-x86-64`、PE32+、Windows CUI；编译器信息字符串显示 GCC 15.2.0 / MSYS2。导入表含 `puts`、`strlen`、`strncmp` 等 C 运行库函数。没有网络、文件写入、命令执行一类导入，符合一个小型本地逆向题附件的特征。

PowerShell 对带中文完整路径的 `objdump` 文件参数出现了字符编码问题，报“找不到文件”。保留了该失败命令与错误输出；随后把同一份 EXE 临时复制到 ASCII 路径 `C:\Users\mzj\Desktop\CTF\challenge527.exe` 再交给 objdump。该副本只用于分析，不是另一个附件，也没有修改原始文件。

### 2. 从字符串中找到 Base64 常量

运行 GNU `strings -t x -a -n 4` 后，发现文件偏移 `0x2400` 处有一段 Base64 文本：

```text
ZmxhZ3swODE3NDE1OC1jY2I1LTRkMDMtOTNhYS05ZWYxfQ==
```

`.rdata` 的 objdump 十六进制转储也从 RVA `0x140004000` 显示同一字节序列，后面紧跟零字节；PE 文件映射中它的文件偏移是 `0x2400`。该字符串不是依据题目名构造出来的猜测，而是附件只读数据节中的原文。

### 3. 看反汇编，确认常量的用途

关键控制流位于反汇编函数 `0x1400029f0`：

1. `0x140002a09` 把 `0x140004000`（`.rdata` 开头）装入 `r10`，即上一步定位到的 Base64 常量。
2. 后续循环按四个 Base64 字符取值，并用移位和按位或拼成一到三个输出字节。这是标准 Base64 解码过程；对应的解码结果暂存于栈缓冲区。
3. 在 `0x140002db5`，程序调用 `0x1400028b8`。此地址是导入跳板，PE 导入表把它映射到 `puts`，所以解码出的字符串会被输出。
4. 可执行文件入口启动 C 运行库，再调用这段用户逻辑。由此可知该常量就是程序运行时解码并打印的目标文本，而不是孤立的诱饵字符串。

### 4. 离线解码、格式检查与正向验证

对字符串执行标准 Base64 解码，得到可读 ASCII：

```text
flag{08174158-ccb5-4d03-93aa-9ef1}
```

将结果重新 Base64 编码，逐字节得到原常量，形成可逆校验。随后直接运行附件程序，程序原样输出相同文本，并以退出码 0 结束。静态数据、解码结果和程序实际输出三者一致。

格式细节：使用小写 `flag`；使用 ASCII 左右花括号 `{`、`}`；UUID 风格分组用 ASCII 短横线 `-`。不要替换成中文全角标点、长横线或其他视觉相似字符。

复现代码保存在 `solve.py`。它从 EXE 文件偏移 `0x2400` 读取以 NUL 结尾的 Base64 文本，用标准库解码，再检查重新编码结果完全等于原串。

## 最终结果

```text
flag{08174158-ccb5-4d03-93aa-9ef1}
```

**置信依据：高。** 候选直接由只读节中的 Base64 常量解出；反汇编确认程序解码该常量并经 `puts` 输出；本地标准库解码、重新编码一致性校验及运行附件所得结果完全相同。主代理随后在玄机平台前台提交，题目页显示“已完成”1/1，并记录账号 slu_mzj 一血。
