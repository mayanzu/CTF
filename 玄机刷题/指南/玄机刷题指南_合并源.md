# 刷题次序与复盘方法

已通过题目按简单到难的顺序学习：先做简单 MISC 和 REVERSE，再做中等 AI、图像取证、PCAP 和 RSA，最后处理 Crypto / REVERSE 极难题。对每题都先核实类型、难度和费用，再下载附件、记录哈希、静态检查格式与内容，形成能被输出验证的假设，最后才在平台提交。

复盘时重点追问：
1. 题目真正给了什么材料、要验证什么结果？
2. 附件格式、路径、编码、区段映射是否被独立确认？
3. 推理依赖的每条规则都能否在题目数据或程序代码中找到证据？
4. 候选是否通过本地独立校验？平台是否确实显示完成？
5. 哪些失败尝试改变了假设？失败输出是否保留？
6. 结果能否由命令记录和文件哈希复现？

# 已有完整逐步记录的 12 题思路总览

本章先给每题的核心思路、关键判据与最终 flag，方便快速回忆；每题的完整推理、命令、输出、失败分支与平台回执在正文对应章节展开。阅读顺序建议按本章从上到下，再进入正文核对细节。

## 1. Veiled Shell（ID 580，MISC / 简单）

**思路：** PCAP 里没有 DNS、没有 TLS，只有 172.28.0.20 与 172.28.0.10:80 之间的纯 HTTP，所以重点不是找明文 flag，而是重组 TCP 流、还原一次 WebShell 上传与后续加密信道。上传体里的 PHP 脚本硬编码了 16 字节密钥 `3f9a7c2e1d8b6045`，请求按 Base64 + AES-128-CBC（未传 IV，实测全零 IV）加密，明文形如 `assert|system('cmd');`，只有 `|` 后半段会被 `eval`。按“Base64 → AES → 去填充”解出每条命令，再按“gzip（若声明）→ AES → Base64”还原回显，逐条对照得到目录结构，最后一条回显就是 flag。

**关键判据：** 密钥在脚本源码里；IV 未显式传入，用全零 IV 解出可读 PHP 即验证；`openssl` 缺失时的回退分支是按 `i+1&15` 置换的 XOR，可与 AES 分支互为印证。

**Flag：** `flag{bcb5e1538d12162510d5297a43fa8fcf}`

## 2. 即随本心（ID 528，REVERSE / 简单）

**思路：** 不运行 EXE。先确认它是 PyInstaller one-file（overlay 约 12.7 MB + `PyInstallerOnefileHiddenWindow` 字符串），再用尾部 Cookie 魔数 `MEI\x0c\x0b\x0a\x0b\x0e` 定位归档索引，解析 TOC 找到类型为 `s`、名字以 `aes` 开头的主脚本条目，zlib 解压后 `marshal.loads` 拿到 code object，只 `dis.dis` 反汇编而不执行。反汇编显示：`sys.gettrace()` 反调试，然后 `base64(iv + AES-CBC(pad(输入))) == 内置常量`，key 与 iv 均为 `1234567890abcdef`。既然比较逻辑是确定的，直接把内置常量按同一参数解密即可还原输入。

**关键判据：** Base64 解码后前 16 字节既是 IV 也等于 key；解密结果再正向加密必须逐字节复现内置常量（`matches expected: True`）。

**Flag：** `flag{316d168f-e854-43a6-9996-5eb10c7efdec}`

## 3. Prompt Trace（ID 590，AI / 中等）

**思路：** 这题考的是“按系统提示执行规则”，不是把 CSV 里的十六进制串全拼起来。`system_prompt.txt` 规定只有同时满足三条才写入碎片：通道 `class=production`、`decision=block`、`intent=exfiltrate`。先把 `channels.json` 里的 `lane_id` 映射到类别（CH-04、CH-17 是 production，CH-11 是 redteam，CH-22 是 eval），再在 `guard_events.csv` 中三重过滤，得到恰好覆盖 shard_idx 0–3 的四条；每条 8 字符 crumb 写入前**反转字符顺序**，最后按 `shard_idx` 升序拼接。

**关键判据：** 空 crumb、`intent=injection`、redteam/eval 通道一律排除；必须按 `shard_idx` 排序而不是按 CSV 行序（CSV 中 shard 2 出现在 shard 0 之前）。

**Flag：** `flag{c4d82a6fd755593832df032275355be0}`

## 4. 班次邮戳（ID 585，MISC / 中等）

**思路：** PNG 的 iTXt 注释写着“邮戳是冷色油墨，字在戳面上”，这是一条元数据线索而不是 flag：先选区域，再选通道。实测圆区内印泥色以 RGB (36,58,196) 为主，蓝分量远高于红分量，于是用 `B - R > 80` 做掩码（命中 15,597 像素），按行优先遍历命中像素，只读**蓝色通道最低位**，每 8 位 MSB-first 打包成字节，直接得到 flag。

**关键判据：** 先试过“圆区内 RGB 三通道交错读最低位”，输出是无效二进制，说明方向对但排列方式错；掩码比圆形包围更精确，能排除圆外纸面噪点。

**Flag：** `flag{2b250f5b7fcbfba8ce5da68f26aa5483}`

## 5. 可疑流量分析（ID 584，MISC / 中等）

**思路：** 系统没有 tshark/scapy，用 Python 标准库手写 PCAP 解析（linktype 276 = Linux cooked v2）。先系统性排除常规流量：HTTP 只有 3 个页面且无注释、FTP 明文口令但只下载 readme、MySQL 走 TLS 无会话密钥；剩下的异常信号是**短时间高频的随机子域名**，全部解析到 sinkhole `10.10.10.1`。把这些标签去掉两位序号前缀，按 `cdn-static.xyz` 家族筛选、去重、按序号排序，得到 61 个 Base32 字符，补 3 个 `=` 后解码即 flag。

**关键判据：** 必须按域名家族分开分析，按时间混排会得到无意义字节；61 mod 8 = 5 正好对应 Base32 的补位规则。

**Flag：** `flag{242bdddd09b6769d2e48404f6e70d38d}`

## 6. babyRSA（ID 358，Crypto / 中等）

**思路：** 题目给了 `d`、`c` 和高精度 `leak`，关键是把 leak 代数化：`leak = (3p²−1)/(3pq) = p/q − 1/(3pq)`，所以 leak 略小于 `p/q`，误差 `< 1/(2q²)`。由连分数逼近定理，用 `Fraction(leak).limit_denominator(2^1024−1)` 做有理重构必然还原既约分数 `p/q`。校验位长与 `p>q`、`gcd=1` 后算 `n=pq`，直接 `m = c^d mod n` 得明文。

**关键判据：** 必须从十进制**字符串**构造 `Fraction`，先转 float 会丢精度；最大分母要设成 `2^1024−1`；给了 `d` 就不需要 `e`。

**Flag：** `flag{th1s_1s_4_ture_fl4g}`

## 7. Tch3s（ID 286，Crypto / 极难）

**思路：** 破点不在 128 位密钥，而在 PRNG 种子：反汇编看到 `time(NULL)` → `srand` → 循环 `rand()` 生成 16 字节密钥，测试明文同样由 `rand()%256` 生成，而 `output` 里公开了首组明文。于是把“Unix 秒级时间”当搜索空间，每个候选种子先跳过 16 次 `rand()` 生成密钥，再比对后续 16 个低字节是否等于已知明文，用明文前 4 字节做快速过滤。命中 `seed=1753843495` 后，把工作副本的 `time()` 改成固定种子、把加密调用改成解密调用 `0x31a1`，用 `FLAG` 环境变量喂入密文分块解密。

**关键判据：** 候选种子必须能完整重现 `720B4455C91B6A024135343386B6679D`；两块分别解密再拼接（整段一次送入时第二块异常，该现象如实保留）；只改工作副本，原附件不动。

**Flag：** `flag{tim1ng_a7t@ck_1s_dangerous}`

## 8. crazyaes（ID 81，REVERSE / 极难）

**思路：** 附件 PE 头有损坏、内部还 UPX，所以先把“修头 / 解包 / 反推 / 运行”拆成独立步骤：复制后修 PE 签名，用官方 UPX 解包得到 527,872 字节的工作副本，再静态定位比较逻辑——读入前 16 字节、跑自定义 AES、与 16 字节目标常量比较。它借用 AES-128 骨架（Nk=4、Nr=10），但每轮有三处自定义：状态 SubBytes 后再 XOR `0xA1`、MixColumns 每输出字节再 XOR `0x54`、每次 AddRoundKey 后再 XOR 固定 16 字节 round mask。另外初始化函数有反调试分支：无调试器时把 key 第 3 字节写成 `h`。

**关键判据：** 必须逐项撤销三处自定义才能逆出明文；用反向解出的候选再**正向复算**必须得到目标常量 `B43836301E6848575101B7039B98E37E`；最后把候选喂给解包副本，输出 `WOW!!!` 而错误候选输出 `wrong!!!`。

**Flag：** `flag{Re_1ts_f0n}`

## 9. tradre（ID 554，REVERSE / 中等）

**思路：** 程序是 fork + `ptrace(PTRACE_TRACEME)` + 满地 `int3` 的反调试壳，父进程在每次陷阱后改写子进程寄存器；把 `int3` 当 nop 直接跳过会立刻“非法指令”，所以纯动态绕行不可行。转折点是题目页的公开 Writeup 给出校验素材：33 字节 `target`、32 字节 `mask`、16 字节 `key`，其中 `target` 要按 `[:16] + [17:33]` 取值（有意跳过下标 16 的 `0x20`），再与 `mask` 逐字节 XOR，最后 AES-128-ECB 解密。为避免照抄，本地用 PowerShell/.NET 脚本独立复算每一步中间值。

**关键判据：** `target` 是 33 字节而非 32 字节，切片跳字节是本题最大的坑；复算出的正文必须是 32 位小写十六进制。

**Flag：** `flag{157692930ce5585ff3f3a67455a03443}`

## 10. 像素囚笼1（ID 583，MISC / 简单）

**思路：** 正确路线是“PNG 尾部附加了 ZIP”，而不是肉眼猜圆点含义：IEND 之后从偏移 4,956 开始是一个完整 ZIP，唯一成员 `secret.txt`，其 general-purpose flag bit 0 被置 1，看起来像 ZipCrypto 加密。真正解法是**识破这个伪造的加密标志**——偏移 4,996 起的 113 字节本身就是一条 raw DEFLATE 流，直接 `zlib.decompress(data, wbits=-15)` 即可解出明文并校验 CRC32 `9d13b619`；跳过所谓“12 字节加密头”反而报 `invalid block type`。明文最后一行是 Base64，解码即 flag。

**关键判据：** 长度 113、流尾标志与 CRC32 三项一致才算解出；此前数百万级口令穷举全部无效，因为 `ZipFile.read(pwd=...)` 和自写校验都会按伪标志跳过前 12 字节，永远碰不到真正的明文。

TOC 中主脚本条目名为 `aes题目加强反调试`，类型为 `s`，压缩长度 1,039 字节，解压长度 1,472 字节。它是 zlib 压缩的 Python marshal code object。用 `marshal.loads` 读取代码对象并用 `dis.dis` 反汇编，只解析字节码，没有执行它。

PyInstaller TOC 核心解析代码如下。TOC 条目记录由 `!IIIIBB` 固定头和 NUL 结尾的名称组成，条目中的数据偏移相对于归档起点：

```python
import struct, zlib, marshal, types, dis

cookie_magic = b'MEI\x0c\x0b\x0a\x0b\x0e'
cookie = data.rfind(cookie_magic)
_, package_len, toc_offset, toc_len, py_version = struct.unpack_from(
    '!8sIIII', data, cookie
)
archive_start = len(data) - package_len
toc_start = archive_start + toc_offset
toc_end = toc_start + toc_len

pos = toc_start
while pos < toc_end:
    entry_size, offset, compressed_len, raw_len, compressed, type_id = \
        struct.unpack_from('!IIIIBB', data, pos)
    raw_name = data[pos + 18 : pos + entry_size].rstrip(b'\0')
    name = raw_name.decode('utf-8', errors='replace')
    if type_id == ord('s') and name.startswith('aes'):
        packed = data[archive_start + offset : archive_start + offset + compressed_len]
        pyc_code = zlib.decompress(packed) if compressed else packed
        main_code = marshal.loads(pyc_code)
        dis.dis(main_code)  # 反汇编查看，不调用 exec/eval
    pos += entry_size
```

## 5. 反汇编得到的程序逻辑

主脚本常量和指令表明：

1. `is_debugging()` 调用 `sys.gettrace()`；若返回非空，就输出“检测到调试器，程序终止。”并退出。这是反调试检查。
2. `key = b'1234567890abcdef'`，`iv = b'1234567890abcdef'`。
3. 创建 `AES.new(key, AES.MODE_CBC, iv)`。
4. 读取用户输入并 UTF-8 编码，使用 PyCryptodome 的 `pad()` 对齐 AES block size（PKCS#7）。
5. 计算 `base64(iv + AES_CBC_encrypt(pad(输入)))`，并与内置目标字符串比较。
6. 完全匹配时输出“密文匹配，正确！”。因此目标字符串可直接作为已知明文 AES 密文来逆向恢复输入，不需要启动程序或绕过调试器。


## 6. AES 解密过程

按代码先 Base64 解码：总长 64 字节。程序把 IV 与密文拼在一起编码，所以前 16 字节是 IV，余下 48 字节是三个 AES block 的 CBC 密文。前 16 字节也与代码中的 key 一致。

然后使用同一 key / IV 做 AES-128-CBC 解密，并移除 PKCS#7 padding，得到：

```text
flag{316d168f-e854-43a6-9996-5eb10c7efdec}
```

可复核的 Python 代码（使用本机已安装的 `cryptography`）：

```python
import base64
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes
from cryptography.hazmat.primitives.padding import PKCS7

key = b'1234567890abcdef'
expected = (
    'MTIzNDU2Nzg5MGFiY2RlZlsf7ftomnVhJSTZsFM/90ZVUQ5GLwSnIogV7pfOo2iJ'
    'lVK8/1XPcBzaPYPZMMl50Q=='
)
raw = base64.b64decode(expected)
iv, ciphertext = raw[:16], raw[16:]

decryptor = Cipher(algorithms.AES(key), modes.CBC(iv)).decryptor()
padded = decryptor.update(ciphertext) + decryptor.finalize()
unpadder = PKCS7(128).unpadder()
flag_bytes = unpadder.update(padded) + unpadder.finalize()
flag = flag_bytes.decode('utf-8')
print(flag)

# 将结果按题目程序的方式重新加密，确认完全等于内置期望密文。
padder = PKCS7(128).padder()
check_data = padder.update(flag_bytes) + padder.finalize()
encryptor = Cipher(algorithms.AES(key), modes.CBC(iv)).encryptor()
check = base64.b64encode(iv + encryptor.update(check_data) + encryptor.finalize())
print('matches expected:', check.decode() == expected)
```

复算输出 `matches expected: True`。这确认 key、IV、模式、padding 和 Flag 都与程序的比较逻辑一致。

# 2025鹏城杯-babyRSA 解题记录

- 平台：玄机；题目 ID：358；类别：Crypto；难度：中等；费用：免费。

## 1. 题目说明

脚本构造 RSA：生成 1024 位素数 p、q，保证 p>q；加密 m 得 c，并给出 d、c 以及高精度小数 leak。题目提示“参数咋这么少呢？”，关键是利用泄漏恢复 p/q，再由 d 直接解密。

附件还把 leak、d、c 的十进制值写在注释中；分析时读取这些已给数据，不需要联网。

## 2. 推导泄漏关系

附件代码计算：

    leak = (3*p*p - 1) / (3*p*q)
        = p/q - 1/(3*p*q)

因此 leak 非常接近有理数 p/q，且略小于它。p、q 是 1024 位素数，所以 2^1023 ≤ q < 2^1024，泄漏公式的误差满足：

    0 < p/q - leak = 1/(3*p*q) < 1/(3*q^2) < 1/(2*q^2)

连分数有理逼近定理说明：若有理数逼近误差小于 1/(2q²)，该分数必是原数的某个连分数收敛分数。附件给出 1024 位有效数字；十进制舍入误差远小于上面的界，因此可用最大分母 `2^1024-1` 做有理重构，恢复既约分数 p/q。两个素数不同且互素，所以分子、分母就是 p、q。

## 3. 具体分析步骤

1. 从玄机题目页确认题目免费，下载附件并记录 SHA256。
2. 查看 `task.py`：脚本公开了 leak、d、c 的十进制注释值；p、q 用 1024 位素数生成。题目并非缺少全部参数，而是希望从 leak 还原因子。
3. 把十进制 leak 作为精确分数输入 `Fraction`，调用 `limit_denominator(2^1024-1)`。有理重构得到的分子、分母即 p、q。
4. 检查 p、q 位数均为 1024、p>q、gcd(p,q)=1；随后算 n=p*q。
5. 已知 RSA 私钥指数 d 和密文 c，直接计算 m=c^d mod n；将整数 m 转成大端字节，得到明文 flag。
6. 在玄机题目页提交明文 flag，平台返回正确提示，题目标为已完成。

以下是复现核心逻辑（省去附件中的长十进制常量，运行时从 `task.py` 注释读取）：

    from fractions import Fraction
    import re
    from pathlib import Path

    s = Path('task.py').read_text()
    leak = re.search(r'#leak = ([0-9.]+)', s).group(1)
    d = int(re.search(r'#d = (\d+)', s).group(1))
    c = int(re.search(r'#c= (\d+)', s).group(1))
    r = Fraction(leak).limit_denominator((1 << 1024) - 1)
    p, q = r.numerator, r.denominator
    n = p * q
    m = pow(c, d, n)
    flag = m.to_bytes((m.bit_length() + 7) // 8, 'big')

## 6. 从 AES 结构逐轮还原自定义变换
程序主体借用了 AES-128 的结构，但不能直接调用标准 AES 解密，因为每轮又添加了自定义操作。逐个辅助函数确认：

### 6.1 密钥扩展
- RotWord 执行字节循环旋转。
- SubWord 直接使用标准 AES S-box，不带下面状态 SubBytes 的额外变换。
- Rcon 通过字节序调整后异或到轮密钥。
- Nk=4、Nr=10，生成 11 组轮密钥。
- AddRoundKey 对 16-byte state 与对应轮密钥逐字节 XOR。

### 6.2 状态变换
- ShiftRows 是标准 AES 行循环左移，行号即偏移量。
- MixColumns 使用标准 AES 矩阵和 GF(2^8) 多项式，xtime 约在 0x43ad70；约简常数为 0x1B。
- 关键自定义点一：状态 SubBytes 在标准 S-box 查表后，再将每个结果字节 XOR 0xA1。注意 key schedule 的 SubWord 不做这一层 XOR。
- 关键自定义点二：MixColumns 的每个输出字节另 XOR 0x54。
- 关键自定义点三：每次 AddRoundKey 后都 XOR 固定 16-byte round mask：
```text
00 01 02 03 01 00 03 02 02 03 00 01 03 02 01 00
```

### 6.3 轮数顺序
程序循环从 round 0 开始：
- round 0 只执行 AddRoundKey(0)，跳过 SubBytes、ShiftRows、MixColumns。
- rounds 1–9 执行 SubBytes → ShiftRows → MixColumns → AddRoundKey，然后 XOR round mask。
- round 10 执行 SubBytes → ShiftRows → AddRoundKey，然后 XOR round mask；与标准 AES 一样省略最后一轮 MixColumns。

因此解密时必须反向撤销每一步，并且必须在逆 MixColumns 前去掉对应的 0x54；round mask 也要在每一轮正确撤销。最初漏掉 round mask、0x54 或 SubBytes 的 0xA1 中任意一项，都会给出完全不同的明文。我们保留了这些错误分支，最终只接受同时满足完整正向复算、程序输出与平台判题的结果。

## 10. 常见误区与复现资料
- 不要直接执行有损坏 PE 头的原附件；对分析副本修复，并先记录原件哈希。

## 二十三、最终 Writeup：ZIP 伪加密标志与直接解压（2026-09-28）

**核心思路更正：** `secret.txt` 根本没有被 ZipCrypto 加密。ZIP 的 local header 与 central directory 中 general-purpose flag bit 0（`flag_bits=0x1`）是伪造的标志位，它让 Bandizip、Python `zipfile` 以及此前所有自写校验程序都先跳过“12 字节加密头”，于是任何口令都不可能解出真正的明文。正确的做法是把偏移 4,996 起的全部 113 字节当作一条 raw DEFLATE 流直接解压。

**逐步推理与复现：**

1. 解析 PNG 与 ZIP 边界：ZIP local header 在偏移 4,956；按文件名长度与 extra field 长度计算出数据起始偏移 4,996；关键字段 `method=8`、`compress_size=113`、`file_size=113`、`CRC32=9d13b619`、`flag_bits=0x1`。
2. 取出完整 113 字节载荷，直接调用 `zlib.decompress(data, wbits=-15)` 按 raw DEFLATE 解压，不跳过任何字节。
3. 解压得到 113 字节明文，其 CRC32 为 `9d13b619`，与 local header 和 central directory 完全一致——**流尾标志、长度、CRC 三项互证**，这才是“解出明文”的证据。
4. 反向验证：跳过前 12 字节再解压会报 `invalid block type`；那 12 个字节（`0dc8b10ec2201000d09daf38`）本身就是 DEFLATE 数据的一部分，不是 ZipCrypto 的随机加密头。

解出的明文：

```text
Congratulations! You found the secret.
Here is your reward:
ZmxhZ3s0YTMxY2FjOWE2NmE4ZTM5OTY5M2Y1NDNhOGM2NmZiOH0=
```

对最后一行严格 Base64 解码得到 `flag{4a31cac9a66a8e399693f543a8c66fb8}`，符合 `flag{}` 加 32 位小写十六进制字符的格式。

**为什么此前数百万次口令穷举全部无效：** 自写 C 穷举程序对这 12 个 DEFLATE 字节运行 ZipCrypto 解密器，并用 CRC 高字节 `0x9d` 的单字节门槛筛选，所谓“命中”只是错误模型下的随机校验碰撞；`ZipFile.read(..., pwd=...)` 同样按伪标志跳过前 12 字节，因此无论口令是否正确都不可能验证出真正的明文。所有以“破解 ZipCrypto 密码”为目标的候选数与排除结论对本题不成立，不能据此声称已穷举真实密码空间。与口令无关的检查——PNG 区块 CRC、附件哈希、几何测量、位平面与滤波器统计——仍然是各自范围内的有效观测，只是它们都不是本题的载荷。

**本题的教训：** 隐写题里“看起来像标准格式”的标志位本身可能就是伪造的；任何依赖该标志的工具链都会被带偏。判断是否真加密，应直接对原始字节做解压尝试并用 CRC 复核，而不是先相信标志位。

## 2026-09-27 攻关：程序结构、解密规则与平台验证

### 页面与附件复核

玄机题目页标题为“第九届‘强网杯’全国网络安全挑战赛tradre”，分类 REVERSE，难度中等，免费，积分 300。页面唯一步骤提示“尝试读取文件/flag获得本题flag”，要求将正确内容放入 `flag{}` 后提交。附件 ZIP 仅含一个 29,160 字节 ELF64 x86-64 文件 `tradre`，没有独立 flag 或远程地址。

### 观察程序结构

1. `strings` 找到 `Input your flag:`、`This is a fake flag!`、`Correct flag! Validation passed.` 等字符串，说明错误路径会打印假 flag，不能把该字面量当成答案。
2. `readelf` 显示入口地址 `0x400910`。入口将 `0x4047cb` 交给 `__libc_start_main`，该函数设置 60 秒 alarm 后 fork。
3. 子进程先调用 `ptrace(PTRACE_TRACEME)`，随后进入 `0x4009f7`；父进程持续 wait/ptrace 观察子进程的断点。主体代码散布大量 `int3`，父进程会在每次陷阱后改写子进程寄存器/栈，再继续执行。
4. 因此不能把所有 `int3` 当普通无操作指令直接跳过。我曾建立仅用于本地实验的 SIGTRAP 处理器，并让其把 RIP 加 1；运行立即触发“非法指令”，证实这种绕过会破坏题目设计的控制流。该失败没有改变原附件。
5. 随后建立 `tradre_ptrace_logger.c`：以 `LD_PRELOAD` 包装 ptrace，但把每次调用继续转交真实 libc ptrace；输出保存到 `题目资料/tradre/分析脚本/tradre_ptrace_trace.log`。输入测试串 `flag{test}` 后程序仍输出 `This is a fake flag!`。日志共 19,813 行，确认正常父子监控路径确实运行；完整原始日志保留为本地分析证据。

### 平台公开 Writeup 给出的解密规则
