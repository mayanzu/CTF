- 平台：玄机 `https://xj.edisec.net/challenges/286`
- 类型 / 难度 / 费用：Crypto / 极难 / 免费
- 题面：详情页没有文字简介；附件提供一个 Linux x86-64 PIE ELF 和名为 `output` 的文本样本。
- 附件目录：`C:\Users\mzj\Desktop\CTF\Tch3s-附件`
- 原二进制 SHA-256：`03d7248be820b1dab28d1ad3754c1bc81c8b1894b432abaa701538b40f505ab6`
- `output` 长度：21,319,816 字节，约 100,000 组测试明密文；原文件 SHA-256：`6cfa28bb5df2b65205a16ac6b33a1bc74efd1ad84f10d6dd22fa1f55f35300eb`

## 解题目标与关键观察

附件输出开头给出 `encrypted flag:`，之后每组包含 `Test N plaintext`、`Test N encrypted` 与 `Test N decrypted`。第一组明文为 `720B4455C91B6A024135343386B6679D`。程序字符串中出现 `FLAG`、`Error: FLAG environment variable not set`、默认测试值和 `encrypted flag:`，说明程序从环境变量读取待加密内容，并会用其内置解密函数还原测试样本。

反汇编发现主函数在 `0x15c1` 调用 `time(NULL)`，紧接着在 `0x15c8` 调用 `srand`；随后循环调用 `rand()` 生成 16 字节密钥。测试明文也由 `rand() % 256` 生成。因此附件中的测试明文可用于穷举 Unix 秒级种子：每个候选种子先跳过生成密钥的 16 次 `rand()`，再检查后续 16 个低字节是否与已知明文完全相同。

密码函数是自定义的 16 字节分组变换：有 16 字节异或、四张字节替换表、行移位和线性混合，含 10 轮变换与派生轮密钥。`0x27b4` 构造轮密钥，`0x30ba` 加密分组，`0x31a1` 解密分组。关键突破不是暴力破解 128 位密钥，而是种子取自秒级时间且输出暴露了由同一 PRNG 生成的明文。

## 逐步操作与推理

1. 从附件目录检查二进制与输出文件，并把文件复制到工作目录的 ASCII 文件名，避免 Windows 中文路径传入 MSYS `objdump` 时被替换成问号。最初直接对中文路径运行 `objdump` 失败，错误信息也保留在完整 transcript 中。
2. 使用 `strings` 找到环境变量 `FLAG`、默认测试 flag 与输出提示；使用 `objdump -d -M intel` 按地址查看函数，重点检查 `0x15c1` 的 `time`/`srand`、`0x27b4` 密钥扩展、`0x30ba` 加密和 `0x31a1` 解密。完整命令与输出见终端 transcript。
3. 先在附件修改时间附近的小区间试种子，没有匹配。之后将 C 搜索程序限制在 2025-01-01 至 2025-10-31 UTC，并用明文头 4 字节快速过滤；遇到前 4 字节相符时再核验完整 16 字节。
4. 搜索结果：`MATCH seed=1753843495`，即 `2025-07-30 02:44:55 UTC`。候选生成的完整首组明文与附件一致：`720B4455C91B6A024135343386B6679D`。
5. 为利用内置解密函数，复制原二进制为 `Tch3s-recover`，只改工作副本：把 `time()` 调用替换成固定种子；把处理环境变量内容的分组函数调用从加密地址改为解密地址；把测试循环上限改为 0，避免每次复现打印 100,000 组。原附件 `Tch3s.bin` 未修改。
6. 用 `FLAG` 环境变量传入 `encrypted flag` 的原始二进制内容（先将十六进制文本转换成字节），让副本调用 `0x31a1` 解密。为避免本地多分组调用出现第二块异常，分别对两个 16 字节密文块单独运行同一副本：
   - 第 1 块密文：`B789EB607A91D08888E2C4C4E4D9573F`
   - 解密输出：`666C61677B74696D316E675F61377440`，ASCII 为 `flag{tim1ng_a7t@`
   - 第 2 块密文：`F5333E4783390B91EDB9D2B4FD2A5FC0`
   - 解密输出：`636B5F31735F64616E6765726F75737D`，ASCII 为 `ck_1s_dangerous}`
7. 拼接得到候选：`flag{tim1ng_a7t@ck_1s_dangerous}`。这里保留题目中的数字与符号原样，不能自行“纠正”为普通英文拼写。
8. 在玄机题目页打开“提交 FLAG”，输入上述候选并提交。平台页面随后显示绿色“已完成”标记，题目状态确认通过。平台验证是最终正确性依据。

## 复现时需要说明的异常与失败

- 第一次补丁脚本把 x86 指令开头误写成 4 个字节，覆盖后续机器码，临时副本以退出码 `-11` 崩溃；修正为单字节 `b8` 后，副本正常运行。该失败未影响原始文件。
- 完整 32 字节密文一次性送入解密副本时，首块可读、次块异常；两块分别输入后均得到可读且连续的 flag 内容，且平台接受拼接结果。此本地多块调用差异尚未完全定位，故指南明确保留它，不把一次完整调用的异常输出隐去。
- 后续单块复现中的随机测试密文输出与原始附件曾不一致；已知测试明文仍一致。报告只把可复核的种子、分块解密文本及平台通过状态作为证据，不把这一现象解释成已解决的算法细节。
- 浏览器截图通过 Computer Use 在本轮会话中实时显示；当前接口未提供可保存的 PNG 文件。最终 PDF 会如实注明截图缺少本地图片文件，不会声称已归档截图。
